# 项目阅读顺序

> 本文所有路径与行数均基于 2026-10-23 实际扫描结果，未核实的项目没有写入。

## 结论先行

**不要按目录顺序读。** 这个项目有 111 个 Java 文件、60 张表、36 个 Vue 页面，按 `admin-server → common → gateway...` 的字母序读，读到第 20 个文件就会失去主线。

正确姿势：**先用 4 份文档建立地图（第 0 轮），再读 common 的 6 个类懂规矩（第 1 轮），然后纵向打穿「提交预约」这一条链路（第 2 轮），最后横向补认证、目录、后台转发（第 3 轮）。** 第 4 轮以后按需。

如果只有两小时：只读第 0 轮 + 第 2 轮。

## 第 1 轮：common 底座（29 个文件里只读 6 个）

这一轮解决一个问题：**这个项目的每个接口都被同一套壳子包着，壳子不看懂，业务代码全是噪音。**

按这个顺序读，前一个不懂就不要往下走：

| 顺序 | 文件 | 读什么 |
| --- | --- | --- |
| 1 | `backend/common/src/main/java/com/warmpaw/application/AccessLevel.java` | 权限枚举，有哪几级（VISITOR / BUYER / ADMIN 之类） |
| 2 | `.../application/RequestContext.java` | 一个请求进来后携带什么身份信息 |
| 3 | `.../controller/support/ApiRequestExecutor.java` | Controller 的统一入口方法签名，注意 `idempotent` 这个布尔参数 |
| 4 | `.../application/BusinessOperationExecutor.java`（152 行） | **全项目最关键的类**：认证 → 事务 → 数据库锁 → 幂等记录，四件事在这里串起来 |
| 5 | `.../application/BusinessHooks.java`（44 行） | 钩子接口，为什么只有订单服务装配实现 |
| 6 | `.../common/ApiException.java` + `.../controller/support/GlobalExceptionHandler.java` | 错误怎么变成 HTTP 状态码 |
| 7 | `.../dto/ApiResponse.java` | 统一响应格式 |

**刻意不读**：`AuthService.java`（775 行）、`RelationalRepository.java`（456 行）、`ResourceMapper.java`（105 行）。这三个留到第 3 轮按需查，现在读会淹死。

**读完应能回答**
- 一个带 `Idempotency-Key` 的 POST 请求，从进 Controller 到事务提交，中间经过哪几层？
- 幂等键的作用域是什么？（用户 + 方法 + 路径 + 键，见 ARCHITECTURE.md 第 47 行）
- 为什么 `BusinessOperationExecutor` 在 common，而 `PaymentWorker` 只在 order-server？

## 第 2 轮：纵向打穿「提交预约」（核心）

选这条链路的原因：它是 README 定义的唯一核心闭环，串起前端、网关、控制器、应用层、领域服务、持久化、定时任务七个层次。

严格按调用顺序读，每一步都问「它把什么交给了下一个」：

| 步 | 文件 | 关注点 |
| --- | --- | --- |
| 1 | `frontend/buyer-web/src/views/Checkout.vue` | 提交预约时前端发了哪些字段（`petId` / `productVersion` / `expectedAmount` / `agreementVersion` / `agreementAccepted` / `visitAt`） |
| 2 | `frontend/shared/api.ts`（51 行） | 请求基址、演示模式开关、幂等键怎么生成和携带 |
| 3 | `backend/gateway-server/src/main/resources/application.yml` | `order-api` 路由命中哪些路径；注意 `ai-api` 必须排在 `/api/**` 兜底之前，这是有原因的 |
| 4 | `backend/order-server/src/main/java/com/warmpaw/controller/buyer/OrderController.java` | **类注释已写明权限模型、幂等策略、字段校验理由**。重点看 `create` 方法，以及 `beginPayment` 为什么固定返回 409 |
| 5 | `backend/order-server/src/main/java/com/warmpaw/application/OrderApplicationService.java`（323 行） | 应用层职责：编排，不含业务规则 |
| 6 | `backend/order-server/src/main/java/com/warmpaw/service/AppointmentService.java`（180 行） | **预约状态机本体**：`create` / `cancel` / `process` / `expire` 四个方法 |
| 7 | `backend/common/src/main/java/com/warmpaw/repository/BusinessRepository.java`（219 行） | 业务写操作接口 |
| 8 | `.../repository/RelationalRepository.java`（456 行） | 只查第 7 步调用到的那几个方法，别顺读 |
| 9 | `backend/common/src/main/resources/schema.sql` | 按行号跳读：`orders`(261)、`order_appointments`(302)、`order_snapshots`(333)、`agreement_versions`(241)、`pet_occupancy`(801) |

## 第 3 轮：横向补三个域

### 3.1 认证登录（最通用，也最值得学）

这个项目有三套登录：密码、短信验证码、微信扫码。先读主流程，再看变体。

1. `backend/admin-server/src/main/java/com/warmpaw/controller/AuthController.java`（458 行）—— 接口清单就是功能清单
2. `backend/common/src/main/java/com/warmpaw/service/AuthService.java`（775 行）—— **不要顺读**，只找三块：`role()` 权限判定、session 校验、密码哈希
3. `.../service/GraphCaptchaService.java` —— 为什么没配置就直接失败，不回退图片验证码
4. `.../service/SmsGateway.java` —— 本地模拟模式怎么把验证码写进 `backend/data/local-inbox/`
5. 配套文档：`docs/GRAPH_CAPTCHA.md`、`docs/ACCOUNT_SECURITY.md`

### 3.2 商品目录（读写分离的典型）

1. `backend/admin-server/src/main/java/com/warmpaw/controller/publicapi/PetController.java`（买家侧读）
2. `.../application/CatalogApplicationService.java`
3. `.../service/CatalogService.java`（写，只在 admin-server）
4. `backend/common/src/main/java/com/warmpaw/service/CatalogReader.java`（跨服务共享的只读快照投影）

**关键问题**：为什么 `CatalogReader` 在 common 而 `CatalogService` 在 admin-server？答案在 ARCHITECTURE.md 第 41 行——订单要持锁校验价格和库存，不能在锁内远程调用。

### 3.3 后台交易转发（微服务里最容易看不懂的地方）

这是「后台确认预约、处理售后」为什么不直连订单服务的原因：

1. `backend/admin-server/src/main/java/com/warmpaw/remote/OrderAdminClient.java` —— OpenFeign 声明
2. `.../remote/AdminTransactionController.java` —— 校验管理员身份后透传 Token、查询参数、请求体和 `Idempotency-Key`
3. `backend/order-server/src/main/java/com/warmpaw/controller/admin/AdminOrderController.java` —— 下游**再校验一次**身份和归属
4. `.../remote/RemoteOrderExceptionHandler.java` —— 连不上返回 503，不自动重试核销和退款

**读完应能回答**
- 为什么网关不给后台请求「授予」管理员身份？
- 订单服务挂了，哪些后台功能还能用，哪些不能？

## 七个坑，先知道省时间

1. **`frontend/node_modules` 有 6442 个文件**，任何搜索都要排除它，否则结果全是依赖。
2. **README 里大量「待补」**（安装命令、访问地址、日志路径）。这是文档没写完，不是你的环境有问题，别去猜命令。README 开头第 5-6 行自己声明了这点。
3. **`schema.sql` 962 行 60 张表，不要通读**。跟着链路查表，一次看 3-5 张。
4. **`docs/DELIVERY_STATUS.md`、`docs/DEMO_MATERIALS.md`、`docs/运营资料准备.md` 是按日期写的快照**，描述的是「某天验收到哪一步」，不是当前状态。README 第 325 行也提醒过。
5. **`docs/项目文件说明与清理建议.md` 第 133 行引用的 `docs/项目完整文件清单.md` 已被删除**（2026-10-23 清理 7.8M 冗余时移除，该文件受 Git 跟踪，需要时用 `git checkout -- docs/项目完整文件清单.md` 恢复）。`项目文件说明与清理建议.md` 本身仍是好用的文件索引。
6. **`WarmPawApplication` 不是启动入口**，只是集成测试的聚合上下文（ARCHITECTURE.md 第 75 行）。真实入口是三个 `*ServerApplication`。
7. **技术栈很新**：Java 25、Spring Boot 4.0.7、Spring Cloud 2025.1.3。网关配置用的是 `spring.cloud.gateway.server.webflux.routes` 这套新结构，和你在网上看到的 Boot 3.x / Spring Cloud Gateway 教程写法不一样。遇到对不上的地方，先怀疑教程版本，不要怀疑代码。

## 一句话记忆法

> 网关只做路由不授予身份 → 每个接口都过 `ApiRequestExecutor` → 写操作在 `BusinessOperationExecutor` 里拿事务和锁 → 业务规则在 `*Service`，编排在 `*ApplicationService` → 交易只在 order-server，目录只在 admin-server → AI 独立进程只读不写。
