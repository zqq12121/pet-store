### P0-2  Repository 层只有一个全表查询入口 ✅ 已完成

> **状态**：2026-10-24 已完成。新增 `Filter`（条件类型）与三个下推入口，社区列表与工作台统计全部改为 SQL 过滤分页。122 项测试通过，含 15 个社区用例。

**结果**：

| 入口 | 签名 | 说明 |
| --- | --- | --- |
| 条件查询 | `list(kind, filters, keyword, keywordFields, offset, limit)` | 条件之间 AND，关键词在多个字段间 OR LIKE |
| 计数 | `count(kind, filters, keyword, keywordFields)` | 只走 `COUNT(*)`，不装配子表 |
| 条件类型 | `record Filter(field, op, value)` | `field` 是业务字段名，内部映射列名并做白名单校验 |

关键设计：
- **字段白名单**：`columnOf()` 拒绝模型里不存在的字段（500 而不是静默返回空），与 `validate` 的立场一致；
- **值永远参数绑定**：SQL 里只拼白名单列名与枚举操作符，不接受 where 字符串；
- **空集合 = 1=0**：`IN ()` 在业务上表示"没有匹配"，不能退化成"不过滤"；
- **LIKE 转义**：用户搜 `100%` 时必须按字面匹配，转义符选 `!` 而非反斜杠（避开 Java/SQL/驱动三层转义）；
- **`LOWER()` 显式小写**：MySQL 默认 collation 大小写不敏感、H2 默认敏感，不显式转换会在两个环境给出不同结果。

改造前后：

| 位置 | 之前 | 之后 |
| --- | --- | --- |
| 社区列表 | 全表 + 7 层内存 filter + `skip/limit` | 1 次条件查询（20 行）+ 1 次 `COUNT(*)` |
| 收藏筛选 | 全表 `community_reaction` | 条件查询（owner/type/status） |
| 工作台 | **`store.list("order")` 调 5 次**，共 11 次全表 | 2 次范围查询 + 7 次 `COUNT(*)` |

**时间范围为什么放宽 1 秒**：`created_at` / `paid_at` 存 ISO-8601 字符串，秒级与毫秒级精度混存时（`…:36Z` 与 `…:36.629Z`），字符串字典序在整秒边界与真实时间序相反。SQL 粗筛两端各放宽 1 秒，再用原有 `day()` 精筛，口径与改造前完全一致。

**2026-11-07 已解决**：`hydrate` 的 N+1 改为按子表批量 `IN`（见下文「技术债」一节）。

**现象**：`backend/common/src/main/java/com/warmpaw/repository/RelationalRepository.java:149`：

```java
public List<Map<String, Object>> list(String kind) {
    return jdbc.queryForList("SELECT * FROM " + m.get("table") + " ORDER BY created_at DESC,id DESC")
        .stream().map(row -> hydrate(m, row, text(row, "id"))).toList();
}
```

`SELECT *`，**没有 WHERE，没有 LIMIT**。而 `hydrate`（同文件 241 行）对每行的每个 `children` 都执行一次 `SELECT * FROM child_table WHERE parent_id=?`，并且**递归**。

于是任何一次 `store.list(...)` 的代价是：

```
1 次全表扫描 + N 行 × M 张子表 次查询（递归）
```

这套入口被下面这些地方用着，全部是「先全查、再内存过滤」：

| 位置 | 干了什么 |
| --- | --- |
| `CommunityService.java:254-263` | 社区列表：全表加载 → 7 层 filter → `skip/limit` 内存分页 |
| `CommunityService.java:250` | 收藏筛选：全表加载 `community_reaction` |
| `TransactionDashboardService.java:68,70,78,84,86,88,94,102` | 工作台 8 项统计，每项一次全表 + N+1 |

**为什么是 P0**：这是架构级问题，不是局部优化。社区内容上千条、订单上千条之后，列表接口会变成几百次 SQL。`backend/API_STATUS.md:44` 自己也承认「其他部分列表仍在内存过滤」，但实际情况比这句更重——连分页都在内存里做。

**怎么修**：给 Repository 加两个带条件的读入口（`list(kind, criteria, offset, limit)` 和 `count(kind, criteria)`），然后把上面三处改成下推 SQL。**不要**一次性重写所有读取——先改社区列表和工作台统计这两处，因为它们是全表扫描最重的。

### P1-2  几乎不打日志 ✅ 已完成

> **状态**：2026-10-24 已完成。日志格式统一、traceId 打通三服务、状态变更全部留痕。

**做了什么**：

| 位置 | 内容 |
| --- | --- |
| `common/resources/logback-spring.xml` | 统一格式 `时间 级别 [线程] [traceId] logger - 消息`，只输出 stdout（容器收集），框架日志压到 WARN |
| `gateway/resources/logback-spring.xml` | 网关单独一份（不依赖 common），reactor/netty 压到 WARN |
| `common/web/TraceIdFilter.java` | Servlet 过滤器：读/生成 `X-Trace-Id` 写入 MDC，响应头回带，`finally` 清理防线程复用串号 |
| `gateway/TraceIdGatewayFilter.java` | WebFlux 全局过滤器：链路起点发号，改写入站请求头，打印访问日志（方法/路径/状态/耗时） |
| `admin/config/FeignTraceConfig.java` | Feign 出站拦截器，把 MDC 的 traceId 透传给 order-server |
| `BusinessRepository.audit()` | **全项目状态变更日志的唯一出口**：一次覆盖 20+ 个写操作调用点 |

**两个关键判断**：

1. **日志不散落到各 service 方法**。`store.audit(...)` 已经覆盖所有需要留痕的写操作（预约创建/取消/确认、订单交付、售后审核、上下架、员工变更、社区处置），在汇聚点打一次等于全部覆盖，既不会漏也不会重复。这也符合"不要给每个方法加日志"的原则。
2. **网关不用 MDC**。WebFlux 一个请求会跨线程迁移，ThreadLocal 语义不成立，traceId 只能作为参数直接传给日志。业务服务是 Servlet 模型，那边才用 MDC。

**安全处理**：`X-Trace-Id` 是外部可控输入，只接受 `[A-Za-z0-9._-]` 且长度 ≤ 64，防止换行符伪造日志行（日志注入）。审计日志只打 action/actor/resource，**不打用户名、手机号、金额**。

**效果**（测试输出可见格式已生效）：

```
2026-10-24 15:10:52.308 ERROR [main] [] c.warmpaw.service.AppointmentSmsWorker - 预约短信发送失败：...
```

**原始记录**：

**现象**：`grep -rn "LoggerFactory" backend --include="*.java"` 只有 6 行命中，落在 4 个类：

- `order-server/.../service/AppointmentSmsNotifier.java`
- `order-server/.../service/AppointmentSmsWorker.java`
- `common/.../web/ApiErrors.java`
- `common/.../controller/support/GlobalExceptionHandler.java`

没有 `logback-spring.xml`，没有 `MDC`，没有 `traceId`。

**为什么是问题**：8 个容器、3 个 JVM。业务出问题时，你只有异常堆栈和数据库，看不到「这个请求经过哪几个服务、卡在哪一步」。

**怎么修**：加 `logback-spring.xml`（统一格式，含时间、级别、线程、logger、消息）+ 一个 `OncePerRequestFilter` 生成 traceId 塞进 MDC，网关透传 `X-Trace-Id`。然后在关键写操作（创建预约、确认、交付、退款）加 info 日志。不需要每个方法都打。

**顺带发现的真实约束**：`PetFavoriteIntegrationTest` 有一个用例**直接读取迁移脚本文件**，连跑两次验证幂等。文件移动后该用例失败——这不是配置问题，而是说明项目本来就有测试在保护"脚本可重复执行"。已更新其路径并加注释说明为什么仍读文件而不是走 Flyway。

**与旧表的关系**：`schema_migrations`（历史手工记录，compose 健康检查在查）与 `flyway_schema_history`（Flyway 版本表）并存，互不干扰。后者从此为准。

**原始记录**：

**现象**：`backend/deploy/` 下 7 个手工 SQL：

```
account-security-migration.sql       community-migration.sql
appointment-migration.sql            employee-management-migration.sql
appointment-sms-outbox-migration.sql pet-favorites-migration.sql
```

项目**有** `schema_migrations` 表（`schema.sql:816`，字段 `version` / `applied_at` / `source_count`），其中 4 个迁移脚本会写入记录（account-security、community、employee-management、pet-favorites）。新建库由 compose 把 `schema.sql` 挂到 `docker-entrypoint-initdb.d` 自动初始化（`compose.yaml` 的 mysql 卷，仅空数据卷时执行）。

### P1-4  四个 God Class 🟡 部分完成（仅拆出密码子领域）

> **状态**：2026-10-24 拆出 `PasswordService`。AuthService 775 → 752 行，密码算法与校验完全独立。

**做了什么**：把 `passwordHash` / `derive` / `passwordMatches`（PBKDF2-HMAC-SHA256、210000 轮、独立随机盐、恒定时间比对）搬到 `common/service/PasswordService.java`（96 行，无状态、无外部依赖）。`AuthService` 保留同名方法做**委托**，调用点零改动。

**为什么只拆这一块**：密码是 AuthService 里唯一"纯函数、零依赖、安全边界明确"的部分。换算法、调轮数、加 pepper 都只动一个文件，且不会碰到认证编排。其余部分继续拆的代价与风险不成比例：

| 待拆部分 | 障碍 |
| --- | --- |
| 会话（`identify`/`login`/`logout`） | `Actor` 是 AuthService 的嵌套 record，被几十处引用（`AuthService.Actor`）。要拆必须先把它提成独立文件并改全部引用，属于跨模块重命名 |
| 授权（`role`/`staff`） | 静态方法，调用点遍布 controller。移到新类等于全项目改调用名，收益只是"看起来分开了" |
| 短信验证码 | 与登录编排强耦合（`smsLogin` 内部调 `login` 签发会话），拆开会产生 AuthService ↔ SmsAuthService 双向依赖 |

**结论**：符合清单自己的原则——"不要为了拆而拆"。其余三个 God Class（`CommunityService` 659、`OrderService` 655、`CatalogReader` 618）同理，等真正要改对应功能时顺手拆，那时有测试和明确需求兜底，风险更低。

**原始记录**：

| 文件 | 行数 | 问题 |
| --- | --- | --- |
| `common/.../service/AuthService.java` | 775 | 密码、会话、微信三套身份、短信、权限判定挤在一起 |

**怎么修**：不要为了拆而拆。优先拆 `AuthService`——它同时是「认证」和「授权」和「第三方登录」，是三个不同变化率的东西。其余三个在真正要改对应功能时再顺手拆。

## P2 · 要扩容才需要动

### P2-1  定时任务没有分布式锁 ✅ 已完成

> **状态**：2026-10-24 已完成。新增 `SchedulerLock`（Redis `SET NX EX` + Lua 比较后删除），三个 `@Scheduled` 任务全部接入。

**实现要点**：

| 任务 | 锁键 | TTL |
| --- | --- | --- |
| `PaymentWorker.reconcile` | `warmpaw:scheduler:order:reconcile` | 55s（调度间隔 60s） |
| `AppointmentSmsWorker.retryDue` | `warmpaw:scheduler:order:sms-retry` | 25s（间隔 30s） |
| `MaintenanceService.cleanTemporaryFiles` | `warmpaw:scheduler:admin:file-clean` | 1h（间隔 24h） |

- **TTL 必须小于调度间隔**，否则上一轮的锁会挡住下一轮；任务卡死时锁过期让别的实例接手，比永久死锁安全；
- **释放用 Lua 比较 owner**：任务超过 TTL 时锁已被别人持有，直接 `DEL` 会误删，导致第三个实例也能进来；
- **无 Redis 时降级为 `true`**（单实例行为）。当前就是单店单实例部署，拿不到锁不等于任务不该跑；测试环境 `app.redis-enabled=false` 正好走这条路径；
- **`MaintenanceService` 改用 `TransactionTemplate`**：原来 `@Scheduled` 与 `@Transactional` 在同一个方法上，加锁会让事务落在锁内部；而且同类自调用 `@Transactional` 根本不生效（代理不拦截 `this` 调用）。

三个任务本身都有幂等保证（`outbox.due` 条件更新认领、支付按 `outTradeNo` 查单、文件删除失败不改状态），加锁减少的是重复劳动，不是唯一防线。

**原始记录**：

`PaymentWorker`、`AppointmentSmsWorker`、`MaintenanceService` 都是单机 `@Scheduled`。一旦 order-server 起两个实例，就会重复对账、重复发短信。

`docs/DELIVERY_STATUS.md:158` 已经写了「多实例扩容、生产压测、公网 HTTPS 也未验收」。**现在不用修**，但要知道这是扩容前的必答题。修法是拿 Redis 做单实例选举（`SET key value NX EX`），项目已经有 Redis。

### 技术债
