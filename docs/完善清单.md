### P0-2  Repository 层只有一个全表查询入口

**现象**：`backend/common/src/main/java/com/warmpaw/repository/RelationalRepository.java:149`：

```java
public List<Map<String, Object>> list(String kind) {
    return jdbc.queryForList("SELECT * FROM " + m.get("table") + " ORDER BY created_at DESC,id DESC")
        .stream().map(row -> hydrate(m, row, text(row, "id"))).toList();
}
```

`SELECT *`，**没有 WHERE，没有 LIMIT**。而 `hydrate`（同文件 241 行）对每行的每个 `children` 都执行一次 `SELECT * FROM child_table WHERE parent_id=?`，并且**递归**。

于是任何一次 `store.list(...)` 的代价是：

```
1 次全表扫描 + N 行 × M 张子表 次查询（递归）
```

这套入口被下面这些地方用着，全部是「先全查、再内存过滤」：

| 位置 | 干了什么 |
| --- | --- |
| `CommunityService.java:254-263` | 社区列表：全表加载 → 7 层 filter → `skip/limit` 内存分页 |
| `CommunityService.java:250` | 收藏筛选：全表加载 `community_reaction` |
| `TransactionDashboardService.java:68,70,78,84,86,88,94,102` | 工作台 8 项统计，每项一次全表 + N+1 |

**为什么是 P0**：这是架构级问题，不是局部优化。社区内容上千条、订单上千条之后，列表接口会变成几百次 SQL。`backend/API_STATUS.md:44` 自己也承认「其他部分列表仍在内存过滤」，但实际情况比这句更重——连分页都在内存里做。

**怎么修**：给 Repository 加两个带条件的读入口（`list(kind, criteria, offset, limit)` 和 `count(kind, criteria)`），然后把上面三处改成下推 SQL。**不要**一次性重写所有读取——先改社区列表和工作台统计这两处，因为它们是全表扫描最重的。

## P1 · 让代码能被改

### P1-1  前端代码被压成不可读 ✅ 已完成

> **状态**：2026-10-24 已完成。提交 `a7c0aec`「前端代码格式化：引入 Prettier 并重排全部源码」，82 个文件，纯格式化、零逻辑改动。

**现象**：物理行数极少，单行极长：

| 文件 | 行数 | 最长一行 |
| --- | --- | --- |
| `frontend/admin-web/src/views/Orders.vue` | 21 | **5830 字符** |
| `frontend/buyer-web/src/views/Checkout.vue` | 11 | 2898 字符 |
| `frontend/admin-web/src/views/Knowledge.vue` | 32 | 1327 字符 |
| `frontend/buyer-web/src/views/Pets.vue` | 73 | 1082 字符 |

整个前端（`buyer-web/src` + `admin-web/src` + `shared`）超过 300 字符的行有 **143 行**。`admin-web/src/views/Dashboard.vue` 只有 9 行，`Pets.vue` 10 行。

功能是完整的——`Orders.vue` 那 21 行里确实塞了表格、筛选、核销弹窗、预约状态机操作。但代价是：

- 无法 code review（一行就是整个组件）
- 无法 diff（改一个字符，整行重写）
- 任何人执行一次 Prettier，会炸出几千行 diff，等于把整个前端变成一次提交

**结果**：

| 指标 | 之前 | 之后 |
| --- | --- | --- |
| `admin/Orders.vue` | 21 行 | 294 行 |
| `Checkout.vue` | 11 行 | 156 行 |
| `Chat.vue` | 22 行 | 333 行 |
| 超 300 字符的行 | 143 | 5（均为 `Legal.vue` 法律条文，Prettier 不折中文字符串） |

**两个必须知道的坑**（都实测踩过）：

1. **`semi` 必须是 `true`**。Vue 模板里的内联多语句处理器 `@click="accepted=true;open=false"` 在 `semi:false` 下会被 Prettier 拆成多行并去掉分号，变成非法模板表达式。`vue-tsc` 查不出来，只有 `vite build` 报 `Error parsing JavaScript expression`。所以 CI 里构建这一步不能省。
2. **从压缩态首次格式化要跑两轮**才收敛（Prettier 的 printWidth 边界问题）。第二轮后 `format:check` 才全绿。

**后续可选**：8 处内联多语句处理器（`Checkout`/`Orders`/`Pet`/`Employees`/`Shop` 五个页面）现在仍是多行写法。抽成方法后即可把 `semi` 改回 `false`，更贴合原有代码风格。

### P1-2  几乎不打日志

**现象**：`grep -rn "LoggerFactory" backend --include="*.java"` 只有 6 行命中，落在 4 个类：

- `order-server/.../service/AppointmentSmsNotifier.java`
- `order-server/.../service/AppointmentSmsWorker.java`
- `common/.../web/ApiErrors.java`
- `common/.../controller/support/GlobalExceptionHandler.java`

没有 `logback-spring.xml`，没有 `MDC`，没有 `traceId`。

**为什么是问题**：8 个容器、3 个 JVM。业务出问题时，你只有异常堆栈和数据库，看不到「这个请求经过哪几个服务、卡在哪一步」。

**怎么修**：加 `logback-spring.xml`（统一格式，含时间、级别、线程、logger、消息）+ 一个 `OncePerRequestFilter` 生成 traceId 塞进 MDC，网关透传 `X-Trace-Id`。然后在关键写操作（创建预约、确认、交付、退款）加 info 日志。不需要每个方法都打。

### P1-3  数据库迁移靠人工执行，没有自动校验

**现象**：`backend/deploy/` 下 7 个手工 SQL：

```
account-security-migration.sql       community-migration.sql
appointment-migration.sql            employee-management-migration.sql
appointment-sms-outbox-migration.sql pet-favorites-migration.sql
practice-shop.sql
```

项目**有** `schema_migrations` 表（`schema.sql:816`，字段 `version` / `applied_at` / `source_count`），其中 4 个迁移脚本会写入记录（account-security、community、employee-management、pet-favorites）。新建库由 compose 把 `schema.sql` 挂到 `docker-entrypoint-initdb.d` 自动初始化（`compose.yaml` 的 mysql 卷，仅空数据卷时执行）。

缺的是：没有 Flyway/Liquibase 的自动发现与执行顺序约束，没有「哪些迁移尚未执行」的查询入口，`appointment-migration.sql` 和 `appointment-sms-outbox-migration.sql` 不在写记录的那 4 个里。所以 `README.md` 只能靠一句「已执行的迁移不要重复执行」来防错。

**为什么是问题**：换台机器、换个环境，谁执行过哪些迁移仍要人查表确认。README 第 276 行的 Q6 就是在讲这个坑。

**怎么修**：引入 Flyway，把这 7 个文件改写成 `V1__`、`V2__` 顺序的脚本，`baselineOnMigrate=true` 让已有库平滑接入。注意：`schema.sql` 962 行 60 张表不要动，它是「新建库」用的，Flyway 只管增量。

## 下一步

原计划的三件事，两件已完成（README、CI），第三件待决策：

### 待决策：前端格式化

**为什么需要先问**：工作区有 **107 个未提交文件**（102 个已修改 + 5 个未跟踪），`git diff` 统计为 `7677 insertions / 29927 deletions`。在这个状态下跑 Prettier，会把格式化 diff 和这批未提交改动混在同一锅里，事后无法区分。

正确顺序是两步提交：

1. 先把现有未提交改动单独提交（或至少 `git stash`），保证工作区干净。
2. 再跑 Prettier，单独提交一次，commit message 写明「纯格式化，无逻辑改动」。

这样以后 `git blame` 出问题时，能一眼认出「这一行是格式化提交，不是业务改动」。

**配置**：项目当前没有 prettier 依赖（`frontend/package.json` 的 devDependencies 里没有）。需要 `npm i -D prettier`，加 `.prettierrc`（建议 `printWidth: 100`、`singleQuote: true`、`semi: true`），并把 `prettier --check` 加进 CI，防止再次被压成一行。

**风险**：格式化会重写全部 141 个超长行，diff 会很大（但因为是第二步单独提交，可随时 `git revert` 整个提交回退）。
